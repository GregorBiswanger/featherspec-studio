## Decisions taken on `/sdd-clarify` findings — foundation specs 0001–0004 (2026-11-16, proxy)

Cross-spec rules first; they bind every spec that touches the topic.

| ID | Topic | Decision |
| --- | --- | --- |
| PD-018 | Spec identity | A spec **entry** is one file and is keyed by its project-relative path (always unique). The **stem** `NNNN-slug` is the join key to plans, archived plans and return notes and the stable reference for consumers while it is unique. A move between lifecycle folders keeps the stem (same spec, new path). A stem change is "removed + new". The four-digit number is a display ID only |
| PD-019 | Duplicates | Same stem in two folders, or one number with two slugs: every file stays its own entry and its own card, each with a duplicate diagnostic. Nothing picks a canonical copy. A duplicated entry is never Ready. (Replaces 0003 A-001) |
| PD-020 | Who detects what | 0002 reports file facts and parse diagnostics only: unreadable file, unknown values, duplicates, orphan plan, dangling link, unverified version. Lifecycle contradictions (folder × spec status × plan status, missing archive link on a `done/` spec) belong to 0003 alone |
| PD-021 | Board-state precedence (0003) | First match wins: (1) folder `done/` → Done, whatever the status; a status other than Implemented/Baseline/Deprecated adds a contradiction diagnostic. (2) plan `Blocked` or a `BLOCKED` return note → Blocked, also for contradictory specs. (3) contradictory or unreadable spec → placed by its folder (backlog → Backlog, active → Active), never Ready or Review. (4) Review. (5) Active. (6) Ready. (7) Backlog |
| PD-022 | Deprecated successor | Read from the spec if the documented link or the text `successor: none — behaviour removed` is present; otherwise "successor: not available". The shape is UNVERIFIED (no real sample): covered by a synthetic fixture and flagged as such |
| PD-023 | Status history baseline | The history is an observation log, best effort. Whenever no earlier entry for a spec exists (first run, pruned, cleared, unreadable store) the cause is *first observed* and there is no old state. Changes that happened while the store was unavailable are not recorded later. Keyed by stem |
| PD-024 | Restart and resume | No "recovery pending" state. At activation every stored run in an open state becomes `Interrupted` (cause: extension host restarted). Resuming an `Interrupted` run is a later, explicit user action owned by 0011 and offered only where the provider declares resume (PD-007) |
| PD-025 | Ownership of run vocabulary | 0004 owns what is stored: the eight run statuses of handoff FR-011.2 as a closed list, and an event envelope whose `type` is an open string. 0009 defines the event taxonomy on top, 0011 the allowed transitions. 0004 depends on 0001 only — no dependency on 0009 or 0011 |
| PD-026 | What "this project's history" means | Runtime data are keyed by the active project's root-folder URI as 0001 reports it. One store per project root. A different project placed at the same path inherits the old history — accepted and documented as a limitation |
| PD-027 | Retention (confirms PD-012 against ADR-002) | Age cap 90 days by default, configurable; command "FeatherSpec Studio: Clear Run History" with a confirmation every time. ADR-002's "last 50 runs / 30 days" is superseded by this. A per-run size cap with a "truncated" marker event stays as ADR-002 proposes; data kept aside as unreadable is removed by the same command |
| PD-028 | Unreadable runtime data | Granularity is the run. An incomplete record (process killed mid-write) is skipped on read wherever it stands and reported once; the file is append-only, existing bytes are never changed, and every append starts on a fresh line. Any other unreadable part marks that one run "history unreadable", its files stay untouched, other runs are unaffected. If the index is unreadable it is rebuilt from the per-run files |
| PD-029 | Secrets in runtime data | Studio masks before storing: (a) the values of credentials it holds itself, supplied by the adapters through a port; (b) the pattern list kept in the repository under `docs/security/secret-patterns.md` (provider tokens, bearer tokens, private-key blocks). Studio does not read `.env` files. Masking is best effort and documented as such; raw provider data are not stored in the MVP |
| PD-030 | Second window | One writer per project store, enforced by a lock with a heartbeat. A second window on the same project reads runtime data, cannot start runs and never changes run statuses; it says why. A stale lock is taken over |
| PD-031 | Project verdicts (0001) | Three verdicts: *project*, *incomplete*, *not a project*. Markers: M1 = root `AGENTS.md` with a `FeatherSpecVersion:` line, M2 = root `.specs/` directory. Both → project. `AGENTS.md` without the line + `.specs/` + `.claude/commands/sdd-*.md` → project with the attribute *legacy*, version "unknown", diagnostic recommending `/sdd-featherspec-update`; it counts as a project everywhere. Exactly one of M1/M2 → incomplete, cannot become active. The `.github/copilot-instructions.md` location is out of scope until a real sample exists. A folder with a root `.featherspec-setup/` directory is *incomplete* whatever its markers say (spec 0014 BR-07, PD-053 (7)) |
| PD-032 | Version line (0001) | The first line of `AGENTS.md` matching `FeatherSpecVersion:` followed by a value, wherever it stands; the value is the first token, a trailing `# comment` is ignored, shown as written. Empty value → "unknown" plus diagnostic. A second such line → first wins plus diagnostic |
| PD-033 | Active project (0001) | The active project is always remembered, also when it became active without asking. A remembered project that disappears keeps its "not found" message until the user selects another one or it returns; if it returns and nothing else was selected, it is active again. Discovery reruns when a workspace folder is added or removed and when root `AGENTS.md` or root `.specs/` appears, changes or disappears — not on changes inside `.specs/`; also when a root `.featherspec-setup/` directory appears or disappears (spec 0014 BR-07, 0001 AC-013 as amended). No status bar entry and no message in a workspace where no folder is a project or incomplete |
| PD-034 | Reading criteria and requirements (0002) | An acceptance criterion is defined where an `AC-NNN` ID is the leading token of a list item or bold paragraph, anywhere in the file. *Uncertain* is decided by the `[Uncertain]` marker only. `FR-` IDs are read the same way (leading token or first table cell). The body is exposed as ordered sections (heading text + raw content); no section is identified by its meaning. A `**Plan:**` link to a missing file is always a diagnostic; the only link that may dangle is an archived plan's `**Spec:**` line |
| PD-035 | Thresholds (0002, 0006, 0007) | Working thresholds, mine, to be re-measured on a real project: full read of a generated 200-spec fixture under 2 s; model updated within 1 s after the file-change event reaches Studio. Measured by an automated test on the fixture; a failed re-measurement reopens the spec |

## Decisions taken on `/sdd-clarify` findings — visual MVP specs 0005–0007 (2026-11-16, proxy)

| ID | Topic | Decision |
| --- | --- | --- |
| PD-036 | Who owns which UI state | The shell (0005) owns every **panel-level** state and its text: no folder, no project, remembered project not found, incomplete project, several projects and none chosen, loading, load error, reload needed, Restricted Mode. The areas (0006, 0007, 0012) own only **in-area** states: zero specs, empty after filtering, runtime data not available, per-column hints. No area repeats a panel-level state or text |
| PD-037 | Two more panel-level states | *Remembered project not found* (0001 AC-010): says which project is missing, offers "Select project" when others exist and "Refresh". *Incomplete project*: names the missing marker per folder from 0001's diagnostics, offers "Open setup guide" and "Refresh" |
| PD-038 | Load error | Appears only for a project-level failure: discovery itself fails unexpectedly, the lifecycle folders of `.specs/` cannot be listed, or host and webview cannot agree on the message protocol. A broken or unreadable single file is never a load error (it is a diagnostic on its card). "Retry" reruns discovery and a full re-read |
| PD-039 | Selected spec | Identified and remembered by stem (PD-018), plus the path while a stem is duplicated (PD-019). A move between lifecycle folders keeps the selection. A stem that disappears clears it, with the notice "Spec <number> is no longer in the project" — one text, used by 0005, 0006 and 0007 |
| PD-040 | Navigation with a target | The shell offers one navigation request: an area plus an optional target — a spec (stem), a run (ID) or a board filter. Areas ask the shell; they never open each other directly. Until the target area exists the request ends on its placeholder |
| PD-041 | Board filters | By board state, by provider ("no run" included), and by a **named spec set** handed in by the caller (label + list of stems) — this is how Mission Control opens "Needs attention". Filters combine with AND, are visible and clearable. No filter or sort by priority: FeatherSpec has no priority field (PD-015); the detail view shows "Priority: not available", cards show nothing. The handoff's priority items are deferred with that reason |
| PD-042 | Spec detail's place | The detail view lives in the Spec Explorer area (list + detail). The board opens it by asking the shell to navigate to Spec Explorer with that spec selected (PD-040). No fifth area |
| PD-043 | Card text and progress | Description: the first non-empty paragraph under the first second-level heading; text before that heading (header lines, handoff reference) is skipped; none → "No summary". Criteria progress on the card and in the detail view come from the same source, 0003's verification summary (traceability rows by state): verified rows out of all rows; no table → "not available". "Last change" is the newer file modification time of spec and plan — 0002's model delivers the modification time of every file it reads as a file fact |
| PD-044 | "Open file" | Offered only where a source file inside the active project exists: spec, plan, archived plan, return note. Never for runs, status history or "No plan yet" |
| PD-045 | Drops and the transition check | The board asks 0003's transition check for every drop and shows its reason on refusal. An accepted Ready → Active request is handed to the start workflow of 0008 with the spec's stem; 0008 checks again itself. Until the files change the card stays in Ready and shows the run's status. Before 0008 exists that drop is refused with "Agent start is not available yet" |
| PD-046 | Mission Control details | No "recovery pending" figure (PD-024); `Interrupted` runs count under attention. A run whose spec is no longer in the project is counted and listed with "spec not found" (matched by stem) under the run figures and recent activity, never as an attention row of a spec. Recent activity shows observed changes that have an old and a new state, *no longer observed*, and *changed while Studio was not running* — never *first observed*. When the runtime store is unavailable, run figures, attention reasons that need runs and all activity show "not available" with the reason; the spec figures work as usual. The drill-down criteria of 0006 are proven by the navigation request it sends (PD-040); what the target shows is proven in 0007 and 0012 |
| PD-047 | UI freshness (replaces "within 1 s of the save" in 0006/0007) | An area shows a change within 500 ms after it receives the model-changed or run-event notification; decided by an automated component test. The model's own budget stays PD-035 |

| PD-052 | Where and how the setup runs **(proxy)** | The button shows in the Studio view while no project is found and while a project is incomplete. | PD-053 | Setup: open points of spec 0014 after `/sdd-clarify` **(proxy)** | (1) The volatile folder is `.featherspec-setup/`, not `.sdd-setup/`: FeatherSpec names its `.sdd-*` folders after the command that owns them, and this one belongs to Studio (0014 OP-001). (2) In an S9 whose folders are all setup-pending, "Copy merge prompt" comes first, "Set up FeatherSpec" second (OP-006). (3) With kept files the completion message starts "FeatherSpec <version> files were added to <folder>." instead of "is set up", and the Output block ends with the next step (OP-007). (4) Links the user placed in the target are written through, as `cp` and `degit` do; the README says so (OP-008). (5) `/sdd-plan` prefers a route to the latest release that needs no API quota; otherwise the failure reason names GitHub's reset time (OP-009). (6) The Output block names every setting that was kept with a value different from the release's (OP-010). (7) OP-002 and OP-003 stand as recommended. (8) No new runtime dependency for reading the archive: Node's own `zlib` plus a small reader in the adapter, covered by tests |
